# Масштабирование баз данных

## Оценка нагрузки

Оценки опираются на допущения, которых нет в условии: доля выигранных аукционов ~15%, CTR ~0,5%. Допущения уточняются по фактическим метрикам после запуска.

| Поток | Через 3 месяца | Через год |
| ----- | -------------- | --------- |
| Bid requests / результаты аукционов | 18 000 в секунду | 50 000 в секунду |
| Показы | ~2 700 в секунду | ~7 500 в секунду |
| Клики | ~15 в секунду | ~40 в секунду |
| Изменения кампаний и бюджетов из кабинета | десятки в секунду | сотни в секунду |

## Репликация Master-Slave (primary - replica)

| Сервис | Схема | Зачем |
| ------ | ----- | ----- |
| Campaign (PostgreSQL) | Primary + синхронная реплика в другой зоне доступности (Patroni) + асинхронная реплика для чтения | Синхронная реплика - автоматический failover без потери подтверждённых изменений. Асинхронная реплика - чтение кабинета и прогрев кеша, не нагружает primary |
| Financial (PostgreSQL) | Primary + синхронная реплика (Patroni) + асинхронная реплика для отчётов и сверок | Потеря проводок недопустима, поэтому подтверждение записи только после записи на синхронную реплику. Отчёты по финансам не конкурируют с приёмом платежей и списаниями |
| Монолит (PostgreSQL), первые 3 месяца | Primary + асинхронная read-реплика | Аналитика уходит с primary, снимается конкуренция с аукционом |
| Redis Cluster | У каждого шарда primary + replica, автоматическое переключение средствами кластера | Отказ узла не останавливает hot path |
| ClickHouse | Каждый шард в двух репликах (ReplicatedMergeTree) | Отказоустойчивость и распределение запросов аналитики между репликами |

Синхронная репликация добавляет к записи задержку сети между зонами (единицы миллисекунд) - это допустимо для Campaign и Financial, так как их записи не на hot path.

## Шардирование

| Данные | Шардировать? | Ключ | Обоснование |
| ------ | ------------ | ---- | ----------- |
| События в ClickHouse (Statistics, Analytics) | Да: 2 шарда на старте, 4 через год | Хеш campaign_id, внутри шарда - партиции по дням | Основной объём данных системы. Все события одной кампании на одном шарде - отчёт по кампании считается без обмена данными между шардами. Партиции по дням позволяют дёшево удалять старые данные |
| Read-модели в Redis | Да, встроенное шардирование Redis Cluster: 3 шарда на старте, 6 через год | campaign_id для ставок и бюджетов, user_id для сегментов | Сегменты пользователей не помещаются в память одного узла, нагрузка на чтение 50 000 RPS распределяется между шардами |
| Топики Kafka | Да, партиции | campaign_id для показов и кликов, request_id для результатов аукционов | Порядок событий одной кампании сохраняется (важно для бюджета), результаты аукционов распределяются равномерно |
| Campaign (PostgreSQL) | Нет | - | Десятки тысяч кампаний, сотни запросов в секунду - один primary с репликами справляется с большим запасом |
| Financial (PostgreSQL) | Нет на горизонте года, подготовка ключа | advertiser_id (если понадобится) | Списания по показам обрабатываются пакетами: одна проводка на кампанию за пакет событий, а не на каждый показ. Так ~7 500 показов в секунду превращаются в сотни транзакций в секунду. Если нагрузка вырастет, шардирование по advertiser_id (Citus) - все операции рекламодателя остаются в одном шарде |

Риск для шардирования по campaign_id - крупные кампании создают неравномерную нагрузку на один шард или партицию. Мониторинг распределения, при перекосе - составной ключ (campaign_id + номер корзины).

## Read replicas для сервиса аналитики

Да, но на разных этапах по-разному:
- **Первые 3 месяца** - read-реплика PostgreSQL монолита. Тяжёлые запросы аналитики уходят с primary, аукцион перестаёт конкурировать с ними за ресурсы. Задержка репликации (секунды) для отчётов допустима.
- **Целевое состояние** - аналитика работает в ClickHouse, реплики шардов ClickHouse распределяют запросы отчётов. Транзакционные базы аналитика не читает вообще, данные приходят через Kafka.

## CQRS (разделение команд и запросов)

| Где | Команды (запись) | Запросы (чтение) | Зачем |
| --- | ---------------- | ---------------- | ----- |
| Campaign → hot path | Campaign Service, PostgreSQL | Read-модель в Redis: ставки, таргетинг, шаблоны | Hot path читает 50 000 раз в секунду, а пишет кабинет сотни раз. Модели и хранилища под эти профили разные |
| Financial → бюджеты | Журнал проводок в PostgreSQL | Остатки бюджетов в Redis для Bidding, отчёты по расходам в ClickHouse | Аукцион проверяет бюджет без обращения к финансовой базе |
| Statistics / Analytics | Поток событий в Kafka | Агрегаты и витрины в ClickHouse | Отчёты читают заранее подготовленные агрегаты |

CQRS не применяется внутри кабинета для простого CRUD кампаний: там нагрузка низкая, и отдельная модель чтения добавила бы сложности без выгоды.

Цена CQRS - согласованность в конечном счёте: read-модель отстаёт от источника на секунды. Для бюджетов это компенсируется правилом свежести и страховым запасом (Task2/bidding-service.md), для отчётов задержка в секунды приемлема.
