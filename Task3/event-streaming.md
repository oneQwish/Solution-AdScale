# Архитектура потоковой обработки событий (Kafka)

Выбор Kafka обоснован в Task1/adr/ADR-003.md. Первые 3 месяца - managed-кластер, через год - кластер в каждом регионе с репликацией через MirrorMaker 2 (failover.md).

## Кластер
- 3 брокера на регион в разных зонах доступности (5 через год).
- Фактор репликации 3, минимальное число синхронных реплик 2: запись подтверждается, когда событие есть минимум на двух брокерах. Отказ одного брокера не останавливает запись и не теряет данные.
- Schema Registry для схем Avro.

## Топики

Именование: `<домен>.<сущность>.v<версия схемы>`.

| Топик | Продюсер | Ключ партиции | Партиций | Подтверждение записи | Хранение |
| ----- | -------- | ------------- | -------- | -------------------- | -------- |
| `rtb.auction-results.v1` | Bidding Service | request_id | 48 | от лидера (допустима редкая потеря, деньги не зависят) | 3 дня |
| `rtb.win-notices.v1` | Delivery Service (win/billing notice партнёра) | campaign_id | 12 | от всех синхронных реплик | 7 дней |
| `ads.impressions.v1` | Delivery Service | campaign_id | 24 | от всех синхронных реплик | 7 дней |
| `ads.clicks.v1` | Delivery Service | campaign_id | 6 | от всех синхронных реплик | 7 дней |
| `campaigns.changes.v1` | Campaign Service (outbox) | campaign_id | 12 | от всех синхронных реплик | компактируемый (последнее состояние каждой кампании бессрочно) |
| `finance.budget-updates.v1` | Financial Service (outbox) | campaign_id | 12 | от всех синхронных реплик | компактируемый |
| `<топик>.dlq` | Потребители | как у исходного | 3 | от всех синхронных реплик | 14 дней |

Почему такие сроки хранения:
- показы, клики и win notice - 7 дней: достаточно, чтобы Financial и Statistics переобработали события после ошибки в коде, обнаруженной в течение недели;
- результаты аукционов - 3 дня: самый большой поток (до 50 000 событий в секунду, около 850 ГБ в сутки через год до сжатия), нужен для статистики и аналитики, которые забирают его в ClickHouse за минуты;
- компактируемые топики хранят последнее состояние каждого ключа бессрочно - из них прогревается кеш (caching.md).

Число партиций задано с запасом под 50 000 RPS: партиция - единица параллелизма потребителей, количество инстансов потребителя в группе не может быть больше числа партиций.

## Схема событий: Avro

| Критерий | Avro + Schema Registry | JSON |
| -------- | ---------------------- | ---- |
| Размер сообщения | Бинарный, без имён полей в каждом сообщении, в 2-4 раза компактнее | Имена полей повторяются в каждом сообщении |
| Контроль формата | Схема проверяется при публикации, некорректное событие не попадёт в топик | Проверки нет, ошибка обнаружится у потребителя |
| Эволюция схемы | Правила совместимости в Schema Registry | Договорённости без проверки |
| Поддержка | Клиенты C++, Go, Python, Node.js; ClickHouse читает Avro из Kafka напрямую | Везде |
| Отладка | Нужен инструмент для чтения | Читается глазами |

Выбор - **Avro**: на потоке в десятки тысяч событий в секунду размер и строгость схемы важнее удобства чтения. Режим совместимости - обратный (BACKWARD): новые поля добавляются только с значением по умолчанию, поэтому потребители со старой схемой продолжают работать. Несовместимое изменение - новый топик с новой версией (`v2`).

### Общие поля всех событий

| Поле | Тип | Назначение |
| ---- | --- | ---------- |
| event_id | string | Уникальный id события, ключ дедупликации у потребителей |
| event_type | string | Тип события |
| occurred_at | timestamp (мс) | Время события у продюсера |
| producer | string | Сервис-продюсер и его версия |
| region | string | Регион, где произошло событие |

### Поля по типам событий

| Событие | Поля |
| ------- | ---- |
| Результат аукциона (`rtb.auction-results.v1`) | request_id, imp_id, partner_id, outcome, no_bid_reason, campaign_id, creative_id, price_micros, currency, candidates_count |
| Показ (`ads.impressions.v1`) | impression_id (= event_id, ключ идемпотентности списания), request_id, imp_id, partner_id, campaign_id, creative_id, advertiser_id, price_micros, currency, site_or_app_id, country, device_type |
| Клик (`ads.clicks.v1`) | click_id (= event_id), impression_id, campaign_id, creative_id, advertiser_id, price_micros (для оплаты за клик), currency |
| Win notice (`rtb.win-notices.v1`) | request_id, imp_id, partner_id, campaign_id, clearing_price_micros, currency, notice_type (win / billing) |
| Изменение кампании (`campaigns.changes.v1`) | campaign_id, version, status, bid_price_micros, currency, priority, targeting, creatives, blocked_categories. Удаление - пустое значение (tombstone), компактирование удаляет ключ |
| Изменение бюджета (`finance.budget-updates.v1`) | campaign_id, version, total_remaining_micros, daily_remaining_micros, spend_rate_micros_per_sec |

Деньги - целые числа в микро-единицах валюты, без дробных типов.

## Группы потребителей

| Группа | Топики | Что делает | Гарантия |
| ------ | ------ | ---------- | -------- |
| `statistics-aggregator` | аукционы, показы, клики, win notice | Пакетная запись в ClickHouse (раз в 1 с или 50 000 событий) | Как минимум один раз, дубли схлопываются движком ReplacingMergeTree по event_id |
| `analytics-marts` | аукционы, показы, клики, изменения кампаний | Витрины для отчётов, справочник кампаний в ClickHouse | Как минимум один раз |
| `finance-billing` | показы, клики, win notice | Списания пакетами, журнал проводок, публикация остатков бюджетов через outbox | Эффективно ровно один раз: дедупликация по event_id в той же транзакции, offset фиксируется после коммита (Task2/reliability.md) |
| `cache-updater` | изменения кампаний, изменения бюджетов | Обновление read-моделей в Redis | Как минимум один раз, запись идемпотентна по version |

Каждая группа читает поток независимо, со своим offset. Падение одной группы не влияет на остальные и на продюсеров.

**Ошибки обработки.** Временная ошибка - повторы с экспоненциальной задержкой (5 попыток). Если событие так и не обработано - оно уходит в DLQ-топик, группа продолжает работу, дежурный получает алерт. После исправления события переигрываются из DLQ.

**Мониторинг.** Отставание каждой группы (consumer lag) в событиях и секундах. Пороги: cache-updater - 5 с (влияет на свежесть бюджетов), finance-billing - 60 с, statistics и analytics - 5 минут.
