# Отказоустойчивость данных

## RPO и RTO по сервисам

RPO - сколько данных допустимо потерять, RTO - за сколько восстановить работу. Значения выбраны от бизнес-последствий: hot path напрямую связан со штрафами партнёра, финансы - с деньгами клиентов, аналитика может подождать.

| Сервис / хранилище | RPO | RTO | Как достигается |
| ------------------ | --- | --- | --------------- |
| Bidding, Ad Server, Delivery (stateless) | не применимо | < 1 мин | Минимум 3 инстанса в разных зонах, Kubernetes перезапускает упавшие, балансировщик исключает их из трафика |
| Redis (read-модели hot path) | не применимо: данные восстанавливаются из источников | < 1 мин при отказе узла, < 15 мин при потере кластера | Реплика у каждого шарда с автоматическим переключением. При полной потере - повторное наполнение из компактируемых топиков Kafka (caching.md), на это время сервисы работают на локальной копии данных |
| Kafka | 0 для подтверждённых событий показов, кликов, изменений | < 5 мин | Фактор репликации 3, подтверждение от двух реплик, брокеры в трёх зонах |
| Campaign (PostgreSQL) | 0 | < 1 мин | Синхронная реплика, автоматический failover через Patroni |
| Financial (PostgreSQL) | 0 | < 5 мин | Синхронная реплика, Patroni. После переключения - автоматическая проверка сходимости балансов |
| Statistics (ClickHouse) | 0 в пределах хранения Kafka (7 дней) | < 1 ч | Две реплики шарда. Потерянные данные переигрываются из Kafka |
| Analytics (ClickHouse) | 24 ч для витрин | < 4 ч | Витрины перестраиваются из событий и данных Statistics |

При потере целого региона (через год, когда регионов два):

| Данные | RPO | RTO |
| ------ | --- | --- |
| Hot path | не применимо | < 5 мин: GeoDNS переводит партнёров во второй регион |
| Campaign, Financial | до 30 с (асинхронная межрегиональная реплика) | < 30 мин: ручное решение дежурного и повышение реплики |
| События Kafka | до 30 с (задержка MirrorMaker 2) | < 30 мин |

Межрегиональная репликация асинхронная: синхронная добавила бы к каждой финансовой транзакции десятки миллисекунд задержки между регионами. Для событий, не дошедших из потерянного региона, Financial Service сверяет списания с отчётами партнёра по win и billing notice.

## Стратегия резервного копирования

Репликация защищает от отказа оборудования, но не от ошибок: удалённые по ошибке данные удалятся и на репликах. Поэтому нужны резервные копии с восстановлением на момент времени.

| Хранилище | Способ | Частота | Хранение | Куда |
| --------- | ------ | ------- | -------- | ---- |
| PostgreSQL Campaign | Полная копия + непрерывный архив WAL (WAL-G), восстановление на любой момент времени | Полная - ежедневно, WAL - непрерывно | 14 дней | Объектное хранилище в другом регионе |
| PostgreSQL Financial | То же | Полная - ежедневно, WAL - непрерывно | 30 дней + ежемесячные копии на срок хранения бухгалтерских документов | Объектное хранилище в другом регионе, с защитой от удаления |
| ClickHouse | clickhouse-backup | Ежедневно | 30 дней | Объектное хранилище |
| Kafka | Резервная копия не делается: события хранятся в топиках по политике хранения и доходят до баз, у которых есть копии | - | - | - |
| Redis | Снимок (RDB) только для ускорения запуска, не для восстановления данных | Раз в час | 24 ч | Локальный диск |
| Схемы Avro, конфигурации Gateway и Kubernetes | Git | При каждом изменении | Бессрочно | Git-репозиторий |

Раз в месяц - учебное восстановление: копия Financial разворачивается в отдельном контуре, проверяется время восстановления и сходимость балансов. Резервная копия, из которой ни разу не восстанавливались, не считается рабочей.

## Соответствие принципам 12-факторных приложений

| Фактор | Как выполняется |
| ------ | --------------- |
| 1. Кодовая база | Один репозиторий на сервис, один артефакт разворачивается во всех окружениях |
| 2. Зависимости | Явно объявлены и упакованы в контейнерный образ, ничего не берётся с сервера |
| 3. Конфигурация | Адреса баз, Kafka, Redis, лимиты и таймауты - в переменных окружения и секретах Kubernetes, не в коде |
| 4. Сторонние службы | PostgreSQL, Redis, Kafka, ClickHouse подключаются по адресу из конфигурации, их замена (например, переключение на реплику) не требует изменения кода |
| 5. Сборка, релиз, выполнение | CI собирает образ, релиз = образ + конфигурация окружения, развёртывание вместо ручного деплоя |
| 6. Процессы | Сервисы hot path stateless: всё состояние в Redis, Kafka и базах, любой инстанс можно убить без потери данных |
| 7. Привязка портов | Каждый сервис сам отдаёт HTTP/gRPC на своём порту |
| 8. Параллелизм | Горизонтальное масштабирование добавлением инстансов (HPA) |
| 9. Утилизируемость | Быстрый запуск (загрузка локального кеша за секунды), корректная остановка: дообработка запросов и сброс буфера продюсера Kafka |
| 10. Паритет окружений | Тестовое окружение на тех же версиях PostgreSQL, Redis, Kafka, ClickHouse в контейнерах |
| 11. Логи | Логи пишутся в стандартный вывод и собираются централизованно, с request_id |
| 12. Административные процессы | Миграции схем и переигрывание DLQ - отдельные задачи Kubernetes из того же образа |

Факторы 6 и 9 напрямую определяют RTO сервисов hot path: stateless-инстанс с быстрым запуском восстанавливается перезапуском за секунды.
