# Database per Service - выбор базы данных для каждого сервиса

## Принципы

- Каждый сервис владеет своими данными. Другие сервисы получают их только через API или события Kafka, прямых запросов в чужую базу и JOIN между базами разных сервисов нет.
- Тип базы выбирается под профиль нагрузки сервиса: транзакции, поток записи или аналитические чтения.
- На hot path нет обращений к дисковым базам данных: только read-модели в памяти (Redis и локальный кеш процесса).
- Переход постепенный (Strangler Fig, Task1/TO-BE.md): сначала данные разделяются на схемы внутри общей PostgreSQL монолита, затем схема переезжает в отдельный инстанс вместе с выделением сервиса.

## Выбор по сервисам

| Сервис | Тип базы данных | Обоснование |
| ------ | --------------- | ----------- |
| Сервис ставок (Bidding) | Redis Cluster (данные в памяти) + локальная копия в памяти сервиса | Сервис только читает: ставки, остатки бюджетов, правила. Нужен ответ за доли миллисекунды при 50 000 RPS, дисковая БД не укладывается в бюджет 15 мс на аукцион. Данные восстанавливаются из событий Kafka и баз-источников, поэтому постоянное хранилище сервису не нужно |
| Сервис кампаний (Campaign) | PostgreSQL | Реляционные связи (рекламодатель → кампании → креативы → таргетинг), транзакции при изменении кампании и её бюджета, строгая консистентность. Объём небольшой (десятки тысяч кампаний), нагрузка - сотни запросов в секунду от кабинета. Команда уже знает PostgreSQL |
| Сервис статистики (Statistics) | ClickHouse | Поток записи тысяч событий в секунду, только добавление без обновлений, агрегации по времени и кампаниям. Колоночное хранение сжимает события в 5-10 раз, вставка пакетами из Kafka. PostgreSQL при таком потоке упирается в запись и индексы - это та проблема, которая описана в AS-IS |
| Сервис аналитики (Analytics) | ClickHouse (отдельная база-витрина на том же кластере) + реплики для чтения | Тяжёлые аналитические запросы по миллиардам строк за секунды. Витрины строятся из событий Kafka и изменений кампаний, запросы аналитики не касаются транзакционных баз. Отдельная база внутри кластера сохраняет владение данными и экономит бюджет по сравнению с отдельным кластером |
| Сервис финансов (Financial) | PostgreSQL | Деньги: ACID-транзакции, журнал проводок и таблица обработанных событий с уникальными ключами (защита от двойного списания), синхронная репликация без потери подтверждённых записей. Требования консистентности важнее скорости |

Дополнительно для сервисов hot path:

| Сервис | Хранилище | Обоснование |
| ------ | --------- | ----------- |
| Ad Server | Redis Cluster (сегменты пользователей, индекс таргетинга) | Определение пользователя и подбор кандидатов на каждый запрос за единицы миллисекунд |
| Delivery Service | Redis (шаблоны креативов) + локальная копия | Разметка баннера без обращения к Campaign Service |

## Как данные попадают из одного сервиса в другой

| Кому нужны данные | Чьи данные | Как получает |
| ----------------- | ---------- | ------------ |
| Bidding, Ad Server, Delivery | Campaign | Событие `campaigns.changes.v1` → Cache Updater → Redis |
| Bidding | Financial (остатки бюджетов) | Событие `finance.budget-updates.v1` → Cache Updater → Redis |
| Financial | Delivery (факты показов и кликов) | Топики `ads.impressions.v1`, `ads.clicks.v1` |
| Statistics, Analytics | Bidding, Delivery, Campaign | Топики аукционов, показов, кликов, изменений кампаний |
| Кабинет | Campaign, Financial, Analytics | REST API сервисов |

Изменения из PostgreSQL публикуются через outbox-таблицу: запись бизнес-данных и события происходит в одной транзакции, отдельный процесс отправляет события в Kafka. Так событие не теряется и не отправляется без записи в базу.

## Переходный период (первые 3 месяца)
Все данные остаются в общей PostgreSQL монолита, добавляется read-реплика для аналитики. Bidding Service уже работает с Redis и не обращается к PostgreSQL. Данные монолита разделяются на схемы по будущим сервисам (campaign, finance, stats) - это готовит выделение на этапах 2-3 дорожной карты.
