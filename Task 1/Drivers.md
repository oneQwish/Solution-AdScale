В связи с ростом и будущей интеграцией с крупной площадкой компании требуется подготовить системы к увеличению нагрузок на несколько ключевых узлов, при этом соблюдая требования партнеров.
## Функциональные требования (после интеграции с DSP)
- Приём и обработка bid request от нового DSP-партнёра по OpenRTB 
- Проведение RTB-аукциона и определение победителя в реальном времени 
- Формирование и показ баннера пользователю 
- Запись событий кликов и показов 
- Списание средств, биллинг, сведение балансов 
- Формирование аналитики и отчётности для рекламодателей 
- Управление кампаниями, бюджетами и ставками через личный кабинет 
## Атрибуты качества (по убыванию приоритета) 
1. Производительность: P95 ≤ 80 мс (требование партнёра), штрафы за деградацию — высший приоритет, система уже работает на пределе (110–120 мс при лимите 100) 
2. Надёжность/доступность - SLA 99,9% в финальном решении, штрафы за downtime, проигранный аукцион = потерянная выручка  
3. Масштабируемость: 18 000 RPS через 3 месяца, 50 000 RPS через год 
4. Сопровождаемость / операционная простота - в штате нет SRE, решение должно быть эксплуатируемо текущей командой без найма 
5. Стоимость решения
## Технические ограничения 
- Нельзя переписать систему полностью, только постепенная миграция 
- Текущий гибридный стек (C++/Go/Python/Node) остаётся базой 
- Кеша, очередей, контейнеризации нет, необходима имплементация с нуля 
- Общая БД Postgres на старте 
## Бизнес-ограничения 
- Срок на промежуточное решение — 3 месяца 
- Бюджет ограничен 
- Обязательна непрерывность бизнеса (миграция без остановки сервиса) 
- Нельзя терять текущих клиентов
