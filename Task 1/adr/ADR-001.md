# ADR-001: AdScale переходит на модульный монолит с выделением Auction/Bidding Engine в отдельный сервис

**Дата:** --.--.----

**Статус:** Принято

## Контекст

Подключение нового DSP-партнёра приведёт к моментальному росту нагрузки на 20% и вдвое через год. Требования партнёра: P95 ≤ 80 мс, штрафы за деградацию и downtime.

Система в текущем виде не может обеспечить соблюдение SLA: P95 на отметке 110-120 мс при текущем лимите 100 мс. Срок приведения системы в готовность к подключению - 3 месяца, с последующей доработкой, общий срок завершения проекта - 1 год.

Бюджет ограничен, полная переработка сервиса невозможна: требует дополнительных материальных и трудовых затрат (текущий штат 35 человек) с обязательным обеспечением непрерывности бизнеса. В штате нет SRE, нет опыта эксплуатации кеша, очередей, контейнеризации.

### Матрица взвешенных решений

| ------------------------------ | --- | ------- | ----------------- | ------ | ------------ |
| SLA задержки аукциона          | 5   | 1 (5)   | 4 (20)            | 3 (15) | 5 (25)       |

| DevOps-зрелость команды        | 4   | 5 (20)  | 3 (12)            | 2 (8)  | 1 (4)        |

| **Итого**                      | -   | **84**  | **93**            | **68** | **78**       |

Рассматривались три альтернативы:

### Альтернатива 1: Монолит
Отклонено. Система уже нарушает свой текущий лимит, рост нагрузки только усугубит деградацию.

### Альтернатива 2: Полный переход на микросервисы сразу
Отклонено. Бюджет, срок 3 месяца и отсутствие SRE делают безопасную декомпозицию и обкатку всей системы за это время нереалистичной - подтверждается матрицей (78, ниже модульного монолита, несмотря на лучший результат по SLA/масштабируемости).

### Альтернатива 3: Модульный монолит + выделение Auction/Bidding Engine
Выбрано. Побеждает в матрице как базовый стиль. Дополнительно - Bidding Engine выделяется отдельным сервисом уже на первом этапе (не просто "готовность к выделению", как в чистом модульном монолите), потому что это единственный компонент, чья задержка напрямую формирует SLA партнёра - тот самый фактор с весом 5, по которому монолит и модульный монолит проигрывают микросервисам сильнее всего.

## Решение

Auction/Bidding Engine выносится отдельным stateless-сервисом, масштабируется независимо (контейнеризация, несколько инстансов за балансировщиком). Остальные компоненты остаются модулями монолита с чёткими границами. Данные на старте - общая Postgres, разъезд не одномоментный. Redis - read-only кеш кампаний/ставок перед Bidding Service. Kafka разгружает запись кликов/показов от Delivery Service, снимает конкуренцию за ресурсы БД с критичным путём аукциона. Read-replica добавляется для Analytics.

Через год - расширение того же принципа: в отдельные сервисы выносятся только компоненты hot path показа рекламы (Рекламный сервер, Bidding Engine, Сервис выдачи). Финансовый сервис, Аналитика, Рекламный кабинет и Сервис статистики остаются модулями - не несут нагрузку 50 000 RPS. Границы и API между ними заданы заранее, дальнейший вынос - по мере необходимости, без редизайна.

## Последствия

### Положительные
Независимое масштабирование самого критичного по SLA компонента. Снижение blast radius - падение Bidding Service не тянет за собой остальной монолит. Read-only кеш и Kafka снимают конкуренцию за БД без немедленного разъезда данных.

### Отрицательные
Сетевой вызов вместо internal call между монолитом и Bidding Service - риск для latency, если не продумать протокол (см. Task2). Read-only кеш требует стратегии инвалидации (см. caching.md, Task3) - иначе устаревшие бюджеты/ставки. Stats/Analytics всё ещё делят БД с частью монолита до полного разъезда данных.

Формальный SLA 99,9% и мультирегион не гарантированы без полноценной SRE-функции. Найм одного SRE (минимум за 3 месяца до конца годового горизонта) - это старт функции, а не полное покрытие: для 99,9%/мультирегиона нужна команда от 3-х, что выходит за рамки этого годового плана. Пока штат не дорос до нужного размера - приоритет на удержание текущих показателей надёжности, а не на рост RPS.

Задачи SRE после найма: мониторинг/алертинг по latency и SLO, health-check и автофейловер для hot path, эксплуатация Kafka и Redis, мониторинг read-replica, пороги Circuit Breaker/Retry, безопасный CI/CD вместо ручного деплоя в prod, on-call и runbook'и, capacity planning под дальнейший рост.
