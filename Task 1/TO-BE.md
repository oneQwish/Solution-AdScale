## Выбор архитектурного стиля

Монолит как есть не подходит: система уже работает на пределе (P95 110–120 мс),
рост нагрузки от нового DSP-партнёра и штрафные SLA партнёра гарантированно
приведут к падениям сервиса при отсутствии изменений.

Полный переход на микросервисы сразу тоже не подходит: бюджет ограничен, срок —
3 месяца, в штате нет SRE — безопасно декомпозировать и обкатать всю систему
за это время нельзя без риска для непрерывности бизнеса.

Выбор: модульный монолит + выделение Auction/Bidding Engine отдельным сервисом.
Это единственный компонент, чья задержка напрямую формирует SLA партнёра, и
его изоляция даёт независимое масштабирование самого критичного узла при
минимальном риске и затратах по сравнению с полной декомпозицией.

## Целевая архитектура (через 3 месяца)

- **Auction/Bidding Engine** вынесен отдельным сервисом, масштабируется
  независимо (контейнеризация, несколько инстансов за балансировщиком)
- **Redis**: кеш кампаний и ставок перед Bidding Service и Ad Server, снимает часть
  синхронных чтений из Postgres в hot path.
- **Kafka** принимает события кликов/показов от Delivery Service вместо прямой
  синхронной записи в Postgres, снимает write-нагрузку и конкуренцию за
  ресурсы БД с критичным путём аукциона
- **Stats и Analytics** читают из Kafka асинхронно, не блокируют аукцион
- Остальные компоненты (Рекламный сервер, Сервис выдачи, Финансовый сервис,
  Рекламный кабинет) остаются **модулями монолита** с чёткими границами
- БД: на старте — общая Postgres, данные не разъезжаются одномоментно;
  для модуля Analytics добавляется read-replica
- Протокол взаимодействия Bidding Service с монолитом — см. Task2

## Целевая архитектура (через год)

Отдельные сервисы (hot path показа рекламы):
1. Рекламный сервер
2. Auction/Bidding Engine
3. Сервис выдачи

Модули монолита (не в hot path, нагрузка на порядки ниже):
1. Финансовый сервис — сводит балансы асинхронно
2. Сервис аналитики — читает из Kafka
3. Рекламный кабинет — UI-трафик рекламодателей
4. Сервис статистики - читает из Kafka, пишет в PG

Внутри монолита: чёткие границы и API между модулями. 

Масштабирование: сервисы hot path - stateless, за API Gateway, контейнерная оркестрация. Модули монолита представляют собой несколько инстансов самого монолита. Создана read-реплика PostgreSQL, снимает значительную часть нагрузки с основной базы.

API Gateway: единая точка входа для всего внешнего трафика: личный кабинет рекламодателя, bid requests от DSP/SSP-партнёров, показ рекламы конечным пользователям. Функции: маршрутизация к нужному сервису, аутентификация и авторизация, rate limiting; подключение новых DSP/SSP-партнёров без изменения API-слоя. Stateless Gateway с горизонтальным масштабированием и балансировщиком позволит пропускать тяжелый трафик насквозь при скачках RPS.

Событийная обработка: Kafka разгружает запись некритичных потоков (клики, показы, обновления кампаний). Одинаково работает для сервисов и для модулей монолита.

SLA: целевой показатель 99,9%. Требует SRE для мониторинга, CI/CD, интеграций, предполагается найм сотрудника в рамках бюджета на реализацию минимум за 3 месяца до окончания проекта. Наличие в штате SRE позволит контролировать SLA, взяв задачи по автоматизации обработки известных сценариев отказа. Показатель в 99,9% потребует дальнейшего расширения штата, во время реализации приоритет на удержание текущих показателей.

Мультирегион: Топология и репликация данных — вне рамок проекта, прорабатывается при росте операционной зрелости.

Мультиплатформенная интеграция: подключение новых DSP/SSP через API Gateway без переписывания API-слоя.

Дальнейшее развитие: рост нагрузки продолжится после 50 000 RPS. Решение расширяемо без пересмотра архитектуры, требует увеличения штата и дальнейшего масштабирования хранилищ. Дальнейшая декомпозиция модулей монолита (Financial, Analytics, Ad Cabinet, Stats) — по мере необходимости, без редизайна: границы и API между ними заданы заранее, SRE к этому моменту уже в штате и берёт на себя выделение.
