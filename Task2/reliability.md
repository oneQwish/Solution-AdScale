# Паттерны надёжности

Принцип для hot path: при любой проблеме зависимости партнёр получает ответ в пределах 80 мс. Лучше ответить «нет ставки» (HTTP 204) и потерять один аукцион, чем ответить поздно или ошибкой и получить штраф. Для финансового контура принцип обратный: скорость вторична, ни одно списание не должно потеряться или повториться.

## 1. Circuit Breaker

Размыкатель стоит на каждом синхронном вызове зависимости. Состояния: закрыт (вызовы идут), открыт (вызовы сразу отклоняются и срабатывает резервная стратегия), полуоткрыт (пропускается небольшое число пробных вызовов).

| Где | Условие размыкания | Время в открытом состоянии | Что происходит при открытом |
| --- | ------------------ | -------------------------- | --------------------------- |
| Gateway → Ad Server | 5 таймаутов или ошибок подряд на инстанс | до 3 успешных health check (раз в 2 с) | инстанс исключается из балансировки (api-gateway.md) |
| Ad Server → Bidding Service | ≥ 20% ошибок или таймаутов за скользящее окно 10 с, минимум 100 вызовов | 5 с | упрощённый выбор в Ad Server (раздел 4) или «нет ставки» |
| Ad Server → Delivery Service | те же параметры | 5 с | «нет ставки» |
| Bidding / Ad Server → Redis | ≥ 20% ошибок за 5 с | 2 с | работа на локальной копии данных (раздел 4) |
| Financial → платёжный шлюз | ≥ 50% ошибок за 60 с | 30 с | пополнение ставится в очередь на повтор, пользователь видит статус «в обработке» |

В полуоткрытом состоянии пропускается 10 пробных вызовов: если успешны - размыкатель закрывается, иначе снова открывается. Пороги стартовые, их уточняют по метрикам после запуска. Состояние каждого размыкателя публикуется метрикой, переход в «открыт» поднимает алерт.

Дополнительно - **изоляция ресурсов (bulkhead)**: у каждой зависимости Ad Server свой пул соединений и ограничение на число одновременных запросов. Медленный Delivery не может занять все соединения и заблокировать вызовы Bidding.

## 2. Повторные попытки с экспоненциальной задержкой

**На hot path повторов нет.** Бюджет вызова Bidding - 10-15 мс, повтор не укладывается в SLA и увеличивает нагрузку на и так деградирующий сервис. Вместо повтора - резервная стратегия.

Повторы применяются в асинхронных и финансовых контурах:

| Где | Базовая задержка | Максимум задержки | Попыток | После исчерпания |
| --- | ---------------- | ----------------- | ------- | ---------------- |
| Продюсеры Kafka (Delivery, Bidding) | 100 мс | 5 с | встроенные повторы клиента в пределах 2 минут | Delivery - сохраняет показы и клики на диск (раздел 4). Bidding - часть событий аукциона можно потерять, деньги от них не зависят |
| Потребители Kafka (Statistics, Financial, Cache Updater) | 200 мс | 30 с | 5 | сообщение в DLQ-топик, алерт |
| Financial → платёжный шлюз | 1 с | 60 с | 6 | операция в статусе «требует проверки», разбор оператором |
| Cache Updater → Redis | 50 мс | 2 с | без ограничения числа попыток | алерт, Bidding перестаёт ставить по устаревшим бюджетам |

Правила:
- задержка перед повтором удваивается с каждой попыткой (100 мс, 200, 400, 800...) до максимума;
- к задержке добавляется случайный разброс (jitter) до 50%, чтобы тысячи клиентов не повторяли запросы синхронно и не создавали волну нагрузки после восстановления сервиса;
- повторяются только временные ошибки (таймаут, сервис недоступен или перегружен). Ошибки в самих данных не повторяются;
- повторяются только идемпотентные операции или операции с ключом идемпотентности (раздел 3).

## 3. Идемпотентность финансовых операций

Kafka и повторы дают доставку «как минимум один раз»: одно событие показа может прийти в Financial Service дважды. Двойное списание недопустимо, поэтому каждая финансовая операция имеет ключ идемпотентности.

| Операция | Ключ идемпотентности | Кто формирует |
| -------- | -------------------- | ------------- |
| Списание за показ | impression_id | Delivery Service при регистрации показа |
| Списание за клик (для кампаний с оплатой за клик) | click_id | Delivery Service |
| Пополнение бюджета | payment_id + Idempotency-Key в запросе к платёжному шлюзу | Financial Service при создании платежа |
| Выставление счёта | advertiser_id + расчётный период | Financial Service |

Как обрабатывается событие показа в Financial Service (целевая архитектура, этап 3 дорожной карты):
1. Потребитель забирает пакет событий (до 1 секунды или нескольких тысяч событий).
2. В одной транзакции PostgreSQL: impression_id всех событий пакета вставляются в таблицу обработанных событий с уникальным индексом. Уже обработанные (повторы) уникальный индекс отсекает, они в расчёт не идут.
3. В той же транзакции по новым событиям создаётся одна проводка на кампанию за пакет и меняется баланс рекламодателя. Так ~7 500 показов в секунду превращаются в сотни транзакций в секунду (Task3/scaling.md).
4. Offset в Kafka фиксируется только после успешного коммита транзакции. Если сервис упал до коммита - пакет обработается заново, дубли отсечёт шаг 2.

Таблица обработанных событий партиционирована по дням, партиции старше срока хранения топика (7 дней) удаляются - повтор события старше этого срока невозможен.

В сумме «как минимум один раз» плюс дедупликация по ключу дают эффект «ровно один раз» для денег. Изменение баланса публикуется в Kafka через outbox-таблицу в той же транзакции, поэтому кеш бюджетов в Redis не расходится с журналом.

## 4. Резервные стратегии

| Что сломалось | Что делаем |
| ------------- | ---------- |
| Сервис ставок не ответил вовремя | Ad Server сам выбирает кампанию с самой высокой ставкой из своей локальной копии данных (дефолтная ставка). Нет данных - «нет ставки» |
| Redis недоступен | Сервисы работают на локальной копии данных до 30 секунд |
| Бюджет кампании давно не обновлялся | По кампании не ставим, чтобы не потратить лишние деньги рекламодателя |
| Delivery Service недоступен | «Нет ставки» |
| Kafka недоступна | Delivery сохраняет события показов и кликов на диск и досылает после восстановления - деньги не теряются |
| Упал один из потребителей Kafka | Остальные работают, упавший после перезапуска продолжает с места остановки |
| Перегрузка | Ad Server сразу отвечает «нет ставки» на часть запросов, чтобы остальные уложились в 80 мс |

## 5. Таймауты и проверки здоровья

- У каждого синхронного вызова есть таймаут (таблица бюджета задержки в interaction.md), deadline передаётся по цепочке gRPC.
- Каждый сервис отдаёт liveness (процесс жив) и readiness (готов принимать трафик: прогрет кеш, есть соединение с Redis). Инстанс не получает трафик, пока не прогрет кеш (Task3/caching.md).
- Graceful shutdown: при остановке инстанс перестаёт принимать новые запросы, дорабатывает текущие и сбрасывает буфер продюсера Kafka.
