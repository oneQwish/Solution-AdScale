# Взаимодействие сервисов и выбор протоколов

## 1. Сводная схема

| Связь | Протокол | Паттерн | Почему |
| ----- | -------- | ------- | ------ |
| DSP-партнёр → API Gateway → Ad Server | OpenRTB 2.6, JSON поверх HTTPS | Синхронный запрос-ответ | Отраслевой стандарт, задан партнёром |
| Ad Server → Bidding Service | gRPC | Синхронный вызов с deadline | Hot path, важна каждая миллисекунда |
| Ad Server → Delivery Service | gRPC | Синхронный вызов с deadline | Hot path, разметка нужна в ответе партнёру |
| Кабинет → Campaign / Financial / Analytics | REST, JSON | Синхронный запрос-ответ | Низкая нагрузка, простота отладки, UI-сценарии |
| Delivery → Statistics / Financial / Analytics | Kafka | Асинхронные события | Показ не должен ждать обработки события |
| Campaign / Financial → Redis (read-модель hot path) | Kafka → Cache Updater | Асинхронные события, CQRS | Hot path не зависит от доступности бизнес-сервисов |

Диаграммы: [diagrams/component.puml](diagrams/component.puml), [diagrams/bid_request.puml](diagrams/bid_request.puml), [diagrams/event_stream.puml](diagrams/event_stream.puml).

## 2. Бюджет задержки

Партнёр измеряет 80 мс на своей стороне, то есть включая сеть. Бюджет разложен по участкам пути, у каждого участка есть таймаут.

| Участок | Бюджет, мс | Таймаут / deadline |
| ------- | ---------- | ------------------ |
| Сеть партнёр ↔ AdScale, TLS (туда и обратно) | 20 | вне нашего контроля, оценка |
| API Gateway: аутентификация, лимиты, проксирование | 3 | - |
| Ad Server: разбор OpenRTB, определение пользователя, подбор кандидатов (локальный кеш + Redis) | 10 | - |
| Ad Server → Bidding Service | 10 | deadline 15 мс |
| Ad Server → Delivery Service (разметка из кеша шаблонов) | 7 | deadline 10 мс |
| Формирование и сериализация ответа | 2 | - |
| Запас на хвосты распределения и пики | 28 | - |
| **Итого** | **80** | Gateway: таймаут upstream 50 мс |

Общий deadline Ad Server на обработку запроса - 45 мс, но не больше `tmax` из OpenRTB-запроса минус 30 мс на сеть и Gateway. Если deadline истёк, Ad Server отвечает «нет ставки» (HTTP 204), не дожидаясь зависимостей. Повторных вызовов на hot path нет - на них нет времени ([reliability.md](reliability.md)).

## 3. Внутреннее взаимодействие: Bidding и Delivery - gRPC

- Трафик полностью внутренний: не нужна совместимость с браузером, CORS и человекочитаемый JSON.
- Жёсткий бюджет задержки: на вызов Bidding Service выделено 10 мс. gRPC работает поверх HTTP/2 с постоянными соединениями и мультиплексированием, бинарный protobuf сериализуется быстрее JSON и занимает меньше места. На 18 000-50 000 RPS это экономит CPU и миллисекунды на каждом запросе.
- Встроенные deadline: таймаут передаётся по цепочке вызовов, сервис видит, сколько времени осталось, и не тратит ресурсы на запрос, который уже не нужен.
- Строгий контракт в `.proto` с обратной совместимостью полей: Ad Server и Bidding Service деплоятся независимо, и изменение формата ответа одним сервисом не ломает другой.
- Поддержка всех языков стека (C++, Go, Python, Node.js).

REST рассматривался и отклонён для hot path: текстовый JSON и отсутствие мультиплексирования в HTTP/1.1 дают лишние миллисекунды и CPU при той же функциональности. Асинхронный вызов не подходит: партнёру нужен ответ в том же запросе.

**Кто оркестрирует.** Ad Server последовательно вызывает Bidding Service, затем Delivery Service и собирает ответ. Bidding Service не вызывает Delivery сам - так у сервиса ставок нет исходящих синхронных зависимостей, и его отказ или медленная работа не каскадируется дальше.

## 4. Данные кампаний (Campaign) - события вместо синхронных вызовов

В hot path никто не вызывает Campaign Service и Financial Service. Ставки, таргетинг и остатки бюджетов попадают в Redis заранее:

1. Campaign Service и Financial Service пишут изменения в свою базу и в outbox-таблицу в одной транзакции.
2. Outbox-публикатор отправляет изменения в Kafka (`campaigns.changes.v1`, `finance.budget-updates.v1`).
3. Cache Updater читает топики и обновляет read-модели в Redis.

Почему не синхронный вызов: при 18 000-50 000 RPS запрос к Campaign Service на каждую ставку либо перегрузил бы его базу, либо добавил бы сетевой хоп с непредсказуемой задержкой прямо в критичный путь. Кроме того, аукцион зависел бы от доступности бизнес-сервисов. Кеш убирает эту связь: hot path зависит только от Redis, а устаревание данных на секунды принимается как компромисс (с защитой бюджета, см. bidding-service.md, «Контроль бюджета»).

Для самого Campaign Service выбран **REST**: его вызывает кабинет рекламодателя, нагрузка низкая (сотни запросов в секунду), важны простота отладки, совместимость с браузером через BFF и стандартные инструменты (OpenAPI).

## 5. Потоковая обработка событий - Kafka

Delivery Service публикует события показов и кликов, Bidding Service - результаты аукционов. Отправитель не ждёт обработки: ответ пользователю и партнёру уходит сразу. Один поток читают независимые потребители (Statistics, Analytics, Financial, Cache Updater), каждый со своей скоростью и своим offset, с возможностью повторной обработки после ошибки. Обоснование выбора Kafka - Task1/adr/ADR-003.md, топики и схемы - Task3/event-streaming.md.

## 6. Внешнее взаимодействие - DSP-партнёр

- **OpenRTB 2.6, JSON поверх HTTPS**, постоянные соединения (keep-alive) - стандарт индустрии, задан партнёром.
- Ответ со ставкой - HTTP 200 и BidResponse, «нет ставки» - HTTP 204 без тела. Это штатный ответ протокола, партнёр не считает его ошибкой.
- Когда наша ставка выигрывает и когда баннер показан, партнёр присылает уведомления (win notice и billing notice). Их принимает Delivery Service через Gateway и публикует события в Kafka.
- Внешний контракт (OpenRTB) заканчивается в Ad Server: там живут адаптеры партнёров, которые переводят запрос во внутреннюю модель. Внутренние сервисы не знают о форматах партнёров, новый партнёр с другим диалектом OpenRTB подключается новым адаптером.

## 7. Нужен ли API Gateway

Да. Причины:

- Три типа внешнего трафика с разной аутентификацией: API-ключ партнёра, сессия/JWT рекламодателя, анонимные показы и клики. Без Gateway эта логика дублировалась бы в Ad Server, кабинете и Delivery.
- Rate limiting per-partner в одной точке.
- Единая точка измерения задержки на входе - ровно то, что видит партнёр.
- Фасад Strangler Fig: переключение маршрутов с монолита на новые сервисы и откат без изменений у партнёров.
- Онбординг новых DSP/SSP конфигурацией маршрута, ключа и лимита.

Выбор - **Kong** (OSS). Обоснование и дизайн - [api-gateway.md](api-gateway.md).
