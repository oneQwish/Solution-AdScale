# API Gateway для DSP-интеграции

## Назначение
Единая точка входа для всего внешнего трафика AdScale: DSP/SSP-партнёры (bid request/response по OpenRTB), конечные пользователи (показы и клики), уведомления партнёров о выигрыше и показе и рекламодатели (личный кабинет). Gateway централизует аутентификацию, rate limiting, контроль таймаутов и измерение задержки, поэтому внутренние сервисы не дублируют эту логику каждый у себя. Одновременно Gateway - фасад Strangler Fig (Task1/TO-BE.md): маршрут переключается с монолита на выделенный сервис без изменений у партнёра и с возможностью отката.

Сам Gateway stateless и масштабируется горизонтально за L4-балансировщиком, поэтому не становится узким местом, хотя через него идёт весь hot path.

## Выбор технологии: Kong (OSS)

| Вариант | Плюсы | Минусы | Итог |
| ------- | ----- | ------ | ---- |
| **Kong OSS** | Производительность уровня NGINX, готовые плагины: key-auth, JWT, ACL, ip-restriction, rate limiting, Prometheus, correlation-id. Настройка декларативным конфигом без программирования | Часть возможностей только в Enterprise (например, mTLS-аутентификация клиентов), нет полноценного circuit breaker в виде плагина | Выбран |
| Envoy | Самые гибкие circuit breaking и outlier detection, нативный gRPC | Сложная конфигурация, требует зрелой эксплуатации уровня Service Mesh, которой у команды нет | Отклонён на этом горизонте, вернуться при появлении SRE-команды |
| Managed cloud gateway | Не нужно эксплуатировать | Меньше контроля над лимитами per-partner и таймаутами в миллисекундах, привязка к облаку | Отклонён |

## Маршрутизация

| Входящий путь | Целевой сервис | Протокол | Таймаут upstream | Повторы |
| ------------- | -------------- | -------- | ---------------- | ------- |
| `/rtb/v1/{partner}/bid` | Ad Server | HTTP, OpenRTB JSON | 50 мс | нет |
| `/rtb/v1/{partner}/win`, `/rtb/v1/{partner}/billing` | Delivery Service (приём событий) | HTTP | 200 мс | нет |
| `/ad/**`, `/click/**` | Delivery Service | HTTP | 200 мс | нет |
| `/api/v1/**` | Кабинет (монолит), по мере выделения - Campaign, Financial, Analytics | REST | 5 с | 1 для GET |

Партнёр указывается в пути: у каждого партнёра свой маршрут, свои лимиты и свои метрики. Новый партнёр со своим диалектом OpenRTB направляется на соответствующий адаптер в Ad Server. Протокол на границе не преобразуется: OpenRTB JSON проксируется в Ad Server как есть, а перевод во внутреннюю модель и вызовы по gRPC делает Ad Server (interaction.md, раздел 6). Так Gateway остаётся простым и быстрым.

## Аутентификация и авторизация

- **DSP/SSP-партнёр** - API-ключ в заголовке (плагин key-auth) плюс белый список IP-адресов партнёра (ip-restriction) и ACL на его маршрут. Партнёр - это система, сессии не нужны, зато доступ конкретного партнёра отзывается одной операцией. mTLS надёжнее, но в Kong OSS не поддерживается, пара «ключ + IP» даёт достаточный уровень для B2B-интеграции.
- **Рекламодатель** - JWT, выданный сервисом авторизации кабинета.
- **Пользователь сайта/приложения** - без аутентификации, показ и клик анонимны. Защита от накрутки - лимиты по IP и подпись ссылок клика.

Gateway проверяет ключ до маршрутизации: невалидный запрос не доходит до сервисов. Внутри доверенной сети сервисы получают `X-Partner-Id`, выставленный Gateway, и не проверяют ключ повторно.

## Rate limiting

| Трафик | Лимит | Ответ при превышении |
| ------ | ----- | -------------------- |
| Новый DSP-партнёр | По договору: его трафик - +20% к текущим 15 000 RPS, то есть ~3 000 RPS сейчас и ~6 000 RPS через год (двукратный рост), плюс 20% запаса на пики. Лимиты существующих партнёров - отдельно, по их договорам | HTTP 429, порог согласуется в договоре, чтобы превышение не считалось нашим отказом |
| Рекламодатель | 50 RPS на аккаунт | HTTP 429 |
| Показы и клики | 20 RPS на IP | HTTP 429 |

Счётчики ведутся локально на каждом узле Gateway, лимит партнёра делится на число узлов. Централизованный счётчик в Redis точнее, но добавил бы сетевой вызов в каждый bid request. Небольшая неточность локального подсчёта на hot path допустима, узлы получают равную нагрузку от балансировщика.

## Circuit Breaker и деградация

В Kong OSS поведение размыкателя реализуется через health checks upstream:
- **пассивные**: инстанс Ad Server исключается из балансировки после 5 таймаутов или ответов 5xx подряд;
- **активные**: исключённый инстанс проверяется запросом к `/health` раз в 2 секунды и возвращается после 3 успешных проверок.

Таймаут upstream на bid-маршруте - 50 мс, повторов нет: повтор не укладывается в 80 мс партнёра.

Размыкатели для внутренних зависимостей (Bidding, Delivery, Redis) и ответ «нет ставки» при их отказе реализованы в Ad Server ([reliability.md](reliability.md)). Такой ответ - HTTP 204, штатный для OpenRTB, в отличие от 5xx, который партнёр засчитывает как отказ.

Остаточный риск: если недоступны все инстансы Ad Server в регионе, Gateway вернёт 503. Защита - минимум 3 инстанса Ad Server в разных зонах доступности и второй регион через год (Task3/failover.md).

## Мониторинг времени отклика

Плагин Prometheus на Gateway отдаёт гистограммы задержки с разбивкой по маршруту и партнёру:
- полная задержка запроса - ближе всего к тому, что видит партнёр;
- задержка upstream (Ad Server и всё за ним);
- собственная задержка Gateway.

Плагин correlation-id выставляет `request_id` (берётся из OpenRTB-запроса), который проходит через Gateway → Ad Server → Bidding → Delivery и попадает в логи и трассировку. Разбор конкретного медленного аукциона сводится к поиску по одному идентификатору.

| Метрика | Порог алерта |
| ------- | ------------ |
| P95 задержки bid-маршрута | > 60 мс в течение 1 минуты (предупреждение), > 70 мс (критично) |
| Доля ответов 5xx на bid-маршруте | > 0,1% за 5 минут |
| Доля ответов 204 | рост в 2 раза относительно обычного уровня - признак деградации зависимостей |
| Доля ответов 429 партнёру | > 1% - партнёр упирается в лимит, пересмотреть договор или мощности |

Порог алерта (60-70 мс) ниже SLA партнёра (80 мс), чтобы команда узнавала о деградации раньше партнёра. Дашборды - Grafana, по одному на партнёра.

## Масштабирование
Gateway stateless, конфигурация хранится декларативно в Git и применяется через CI/CD (режим без базы данных). Горизонтальное автомасштабирование по CPU и RPS: скачок трафика от партнёра добавляет инстансы Gateway. Минимум 3 инстанса в разных зонах доступности.

## Онбординг новых партнёров (DSP/SSP)
Новый партнёр подключается конфигурацией: маршрут, API-ключ, белый список IP, лимит и дашборд. Если диалект OpenRTB партнёра отличается - добавляется адаптер в Ad Server. Бизнес-логика внутренних сервисов не меняется.
