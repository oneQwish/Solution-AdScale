# Bidding Service - спецификация сервиса ставок

## 1. Назначение
Bidding Service проводит аукцион по каждому bid request: взвешивает ставки кампаний-кандидатов, применяет бизнес-правила, проверяет бюджет и определяет победителя и цену. Это первый сервис, выделяемый из монолита (Task1/adr/ADR-001.md), так как его задержка напрямую формирует SLA партнёра.

## 2. Границы сервиса

| Входит в сервис | Не входит (кто отвечает) |
| --------------- | ------------------------ |
| Взвешивание ставок кандидатов, приоритеты | Приём и разбор OpenRTB-запроса, адаптеры партнёров (Ad Server) |
| Бизнес-правила аукциона: bid floor, блок-листы категорий партнёра | Определение пользователя и подбор кандидатов по таргетингу (Ad Server) |
| Проверка остатка бюджета кампании перед ставкой | Списание средств и балансы (Financial Service) |
| Выбор победителя и расчёт цены | Формирование разметки баннера (Delivery Service) |
| Публикация результата аукциона в Kafka | Управление кампаниями и ставками (Campaign Service) |

Граница проведена так, чтобы в сервисе не было ни одного синхронного вызова другого сервиса и ни одной записи в базу данных: всё, что нужно для аукциона, читается из Redis и локального кеша. Это делает сервис stateless и позволяет масштабировать его простым добавлением инстансов.

## 3. API

Один метод - **провести аукцион**. Вызывает Ad Server по gRPC (обоснование в [interaction.md](interaction.md)), на вызов отведено 15 мс.

| | Что передаётся |
| - | -------------- |
| На вход | Id запроса, партнёр, места показа с минимальной ценой партнёра, кампании-кандидаты от Ad Server, контекст (гео, устройство, площадка) |
| На выход | По каждому месту показа: победитель и цена или «нет ставки» с причиной (нет кандидатов, ниже минимальной цены, нет бюджета) |

Если сервис не ответил за 15 мс или недоступен, Ad Server отвечает партнёру «нет ставки» ([reliability.md](reliability.md)).

## 4. Логика аукциона

1. Взять ставки и остатки бюджетов кандидатов из кеша.
2. Отбросить кампании на паузе, без бюджета, со ставкой ниже минимальной цены партнёра, с запретом на площадку.
3. Выбрать кампанию с самой высокой ставкой с учётом приоритета.
4. Цена - ставка победителя (first-price аукцион, стандартный для OpenRTB 2.6).
5. Вернуть результат Ad Server и отдельно, не задерживая ответ, отправить событие аукциона в Kafka.

### Контроль бюджета
Главный риск - потратить больше бюджета рекламодателя: при 18 000 RPS кампания за несколько секунд может выиграть тысячи показов. Поэтому:
- остаток бюджета лежит в кеше, Financial Service обновляет его при каждом изменении и раз в 10 секунд для всех активных кампаний;
- если остаток давно не обновлялся (дольше 30 секунд), по кампании не ставим: лучше упустить показ, чем потратить чужие деньги;
- кампания выходит из аукциона заранее, когда остатка хватает меньше чем на 10 секунд показов.

Перерасход ограничен несколькими секундами показов, окончательно деньги списывает Financial Service по фактическим показам.

## 5. Зависимости

| Зависимость | Зачем | Что если недоступна |
| ----------- | ----- | ------------------- |
| Redis (кеш) | Ставки, бюджеты, правила партнёров | Работаем на локальной копии данных ([reliability.md](reliability.md)) |
| Kafka | Отправка результатов аукциона | Результаты копятся в памяти и отправляются позже, на ответ партнёру не влияет |
| Campaign и Financial Service | Источники данных для кеша | Прямой связи нет, данные приходят в кеш через Kafka |

## 6. Модель данных

Своих данных у сервиса нет: кампании принадлежат Campaign Service, бюджеты - Financial Service. Bidding Service читает их копию в кеше.

| Данные | Что внутри | Откуда |
| ------ | ---------- | ------ |
| Ставка кампании | Ставка, приоритет, статус, площадки, где показ запрещён | Campaign Service |
| Бюджет кампании | Общий и дневной остаток, время последнего обновления | Financial Service |
| Правила партнёра | Минимальная цена, запрещённые категории | Настройки партнёра |
| Результат аукциона (выход) | Запрос, победитель, цена, причина отказа | Публикует сам сервис в Kafka |

Деньги хранятся в целых числах (в миллионных долях валюты), чтобы не было ошибок округления.

## 7. Идемпотентность
Аукцион деньги не списывает, поэтому двойного списания из-за него быть не может. Деньги списываются только по факту показа в Financial Service, повтор одного и того же показа там отсекается ([reliability.md](reliability.md)). Повторно аукцион по тому же запросу не проводится - на это нет времени.

## 8. Характеристики

| Параметр | Значение |
| -------- | -------- |
| Время на аукцион | до 15 мс, цель внутри сервиса - 5 мс |
| Нагрузка | 18 000 RPS через 3 месяца, 50 000 RPS через год |
| Масштабирование | Добавлением инстансов, минимум 3 на регион |
| Язык | C++ (переиспользуется код Auction Engine из монолита) |
| Мониторинг | RPS, время ответа, доля «нет ставки» по причинам |
