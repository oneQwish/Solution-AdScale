### Внутреннее взаимодействие: Ad Server - Bidding Service

**gRPC**:

- Трафик полностью внутренний - не нужна совместимость с браузером, не нужен CORS, не нужен человекочитаемый JSON.
- Жёсткий бюджет задержки: у нас всего 80 мс от DSP-партнёра на весь путь, и это внутренний хоп съедает часть бюджета при каждом запросе. gRPC на HTTP/2 с бинарным protobuf быстрее сериализует и передаёт, чем JSON/REST - на масштабе 18 000+ RPS разница ощутима, а не косметическая.
- Строгая типизация контракта (.proto) - снижает риск того самого сценария из урока про Gateway: «один сервис поменял формат ответа, другой упал». Ad Server и Bidding Service деплоятся независимо, значит нужен контракт, который не молча расходится.

### Bidding Service - данные кампаний (Campaign)

Bidding Service читает кампании и баннеры из Redis-кеша, который асинхронно синхронизируется из read-реплики Postgres.

Почему не синхронный вызов: при 18 000–50 000 RPS на аукцион синхронный REST/gRPC-запрос к монолитному модулю на каждую ставку либо положил бы Postgres/adCabinet, либо добавил бы сетевой хоп с непредсказуемой задержкой прямо в критичный путь, да ещё и сделал бы Bidding Service зависимым от доступности монолита - при деградации adCabinet отваливался бы весь аукцион. Кеш убирает эту связь: Bidding Service зависит только от Redis, а актуальность данных - компромисс на секунды/минуты синхронизации, который принимается как приемлемый.

### Потоковая обработка событий (клики/показы) - Kafka
Асинхронный вызов: Delivery Service генерирует событие клика/показа и не должен ждать, пока Statistics/Analytics/Financial Service его обработают. Обоснование выбора именно Kafka указано в ADR-003.

### Внешнее взаимодействие - DSP-партнёр
**OpenRTB поверх REST/HTTPS** - это отраслевой стандарт интеграции, не наш выбор с нуля, но важно явно зафиксировать: внешний контракт (OpenRTB/JSON) и внутренний (наш gRPC) - разные протоколы, и точка их стыковки - API Gateway (см. ниже), а не сам Ad Server.

### API Gateway

Необходим:

- Три типа внешнего трафика с разными требованиями к аутентификации (сессия/JWT для рекламодателя, API-ключ/mTLS для DSP-партнёра, анонимный доступ для показа/клика) - без Gateway каждая эта логика дублировалась бы в Ad Server, adCabinet и Delivery Service по отдельности.
- Преобразование протокола: внешний OpenRTB/REST → внутренний gRPC должно происходить в одном месте, а не размазываться по сервисам.
- Rate limiting per-partner - критично при 18 000+ RPS от одного DSP-партнёра, лимит должен быть виден глобально, а не по каждому сервису отдельно.
- Онбординг новых DSP/SSP-партнёров - конфигурацией маршрута, без redeploy внутренней логики.

Выбор конкретной реализации - **Kong** (NGINX + Lua в основе, готовые плагины под JWT/key-auth/rate limiting, поддержка проксирования к gRPC-бэкендам, не требует отдельного специалиста по Lua или зрелой Service Mesh-эксплуатации, которой у нас пока нет).
