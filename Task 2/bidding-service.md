### Модель данных

Bidding Service не владеет данными — только читает их из кеша. С точки зрения архитектуры важны две сущности и паттерн доступа к ним, а не конкретный синтаксис хранилища.

**Кампания**

| Поле                                  | Назначение                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------ |
| campaign_id                           | идентификатор кампании                                                                           |
| bid_price                             | ставка кампании в аукционе                                                                       |
| priority                              | вес кампании при прочих равных условиях                                                          |
| таргетинг (гео, устройство, площадка) | критерии, под которые кампания подходит                                                          |
| banner_id                             | ссылка на баннер — непрозрачная для Bidding Service, просто передаётся дальше в Delivery Service |
| budget_status                         | активна / бюджет исчерпан — обновляется асинхронно при синхронизации кеша из read-реплики        |

**Паттерн доступа.** Ключевое архитектурное требование к этому кешу — не точечный доступ по campaign_id, а поиск «какие кампании подходят под эту комбинацию гео + устройство + площадка» по каждому запросу. Это определяет, что кеш должен поддерживать выборку по таргетинг-критериям, а не только чтение по ключу — то есть Redis здесь используется не просто как key-value store, а с индексом под этот паттерн поиска. Дальше кампании-кандидаты взвешиваются по bid_price/priority, выбирается победитель, его banner_id уходит в вызов Delivery Service вместе с render_context из исходного запроса.

**Идемпотентность.** Отдельного механизма не нужно: Bidding Service не пишет состояния и не имеет побочных эффектов — повторный запрос с тем же request_id просто пересчитает тот же результат из того же состояния кеша. Это бесплатное свойство stateless-сервиса, не то, что нужно проектировать отдельно. Реальная забота об идемпотентности — у Financial Service, где повторная обработка события из Kafka может задвоить списание.
