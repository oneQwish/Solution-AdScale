## API Gateway

### Назначение
Единая точка входа для всего внешнего трафика AdScale: рекламодатели (личный кабинет), DSP-партнёр (bid request/response по OpenRTB) и конечные пользователи (показ баннера, обработка клика через Delivery Service). Централизует маршрутизацию, аутентификацию и rate limiting в одном месте - так внутренние сервисы (включая новый Bidding Service) не дублируют эту логику каждый у себя, а новый DSP/SSP-партнёр подключается конфигурацией маршрута, а не переписыванием API-слоя.

Сам Gateway stateless и масштабируется горизонтально за балансировщиком - поэтому не становится узким местом, несмотря на то что через него идёт весь трафик, включая hot path показа рекламы.

### Маршрутизация

| Входящий путь                                | Целевой сервис                 | Протокол              |
| -------------------------------------------- | ------------------------------ | --------------------- |
| `/api/v1/campaigns/**`, `/api/v1/reports/**` | Advertiser Dashboard (монолит) | REST                  |
| `/rtb/v1/bid`                                | Ad Server → Bidding Service    | REST (OpenRTB) → gRPC |
| `/ad/**`, `/click/**`                        | Delivery Service               | REST                  |

### Преобразование протокола
DSP-партнёр говорит с AdScale по OpenRTB - это REST/JSON снаружи. Внутри же Ad Server и Bidding Service общаются по gRPC (решение из bidding-service.md - нужна низкая задержка на hot path). Gateway - точка, где это стыкуется: принимает внешний REST-запрос по `/rtb/v1/bid`, транслирует его в gRPC-вызов к Ad Server. Внешний контракт (OpenRTB) и внутренний контракт (наш gRPC) меняются независимо - DSP-партнёр не знает и не должен знать, что происходит внутри.

### Аутентификация и авторизация
Разные схемы под разные типы трафика:

- **Рекламодатель** - сессионная аутентификация / JWT, обычная веб-авторизация личного кабинета.
- **DSP-партнёр** - API-ключ или mutual TLS (стандарт для OpenRTB-интеграций между площадками) - партнёр не человек, сессии не нужны, зато важно уметь быстро отозвать доступ конкретному партнёру при нарушении SLA с его стороны.
- **Пользователь сайта/приложения** - без аутентификации: показ баннера и клик анонимны.

Gateway проверяет токен/ключ до маршрутизации - если невалиден, сервис даже не узнает о запросе. Внутри доверенной сети сервисы могут полагаться на заголовок (например `X-DSP-Partner-Id`), выставленный Gateway, не валидируя ключ повторно.

### Rate Limiting
Лимиты - per-partner/per-client, не глобальные:

- DSP-партнёр - отдельный лимит под его 18 000 RPS (+20% сразу, x2 через год), настраивается в конфиге партнёра.
- Рекламодатель (личный кабинет) - свой, на порядки меньший лимит, другой профиль нагрузки (редкие тяжёлые запросы, не поток).
- Неаутентифицированный трафик (показ/клик) - лимит по IP, защита от накрутки кликов.

Rate limiting на Gateway эффективнее локального: он видит весь трафик, и партнёр, упёршийся в свой лимит на одном маршруте, не может «обойти» его через другой.

### Observability
Gateway - единая точка логирования всего входящего трафика: request_id, путь, статус, latency, upstream-сервис и его собственная latency. Для AdScale это особенно важно на `/rtb/v1/bid` - DSP-партнёр штрафует за деградацию latency, и без единого request_id, который сквозняком проходит через Gateway → Ad Server → Bidding Service, разбор конкретного медленного или упавшего аукциона займёт часы вместо минут.

### Circuit Breaker
Если Ad Server (или дальше по цепочке - Bidding Service) деградирует и перестаёт укладываться в бюджет задержки, Gateway перестаёт слать ему запросы и сразу возвращает быстрый отказ вместо того, чтобы копить очередь и гарантированно сорвать SLA партнёра в 80 мс. Это отдельный уровень защиты от Circuit Breaker внутри самого Bidding Service (тот защищается от Redis) - здесь Gateway защищает весь путь целиком от деградации на входе.

### Масштабирование
Gateway stateless, горизонтальное масштабирование за балансировщиком - тот же принцип, что у остального hot path. Скачок RPS от DSP-партнёра добавляет поды, а не упирается в Gateway как в потолок.

### Онбординг новых партнёров (DSP/SSP)
Новый партнёр подключается добавлением конфигурации маршрута, ключа аутентификации и лимита - без переписывания API-слоя и без redeploy бизнес-логики внутренних сервисов.

### Выбор технологии
Kong (построен поверх NGINX + Lua). Обоснование: производительность на уровне NGINX - критично для 18 000+ RPS на hot path; готовые плагины под JWT-аутентификацию, key-auth для партнёров и rate limiting «из коробки» - не нужен отдельный разработчик, пишущий кастомную Lua-логику, а у нас пока нет даже одного SRE (см. Task1); поддерживает проксирование к gRPC-бэкендам - нужно для связки с Ad Server. Альтернатива - Envoy - мощнее, но требует зрелой эксплуатации (Service Mesh-уровень), это не соответствует текущей стадии команды. Managed cloud-gateway рассматривался, но даёт меньше контроля над кастомной логикой rate limiting per-partner и создаёт vendor lock-in раньше, чем нужно на этом горизонте.
