# TO-BE: целевая архитектура AdScale

Документ опирается на [AS-IS.md](AS-IS.md) (диагностика) и [Drivers.md](Drivers.md) (драйверы). Ключевое решение по стилю зафиксировано в [ADR-001](adr/ADR-001.md), по потоковой обработке - в [ADR-003](adr/ADR-003.md). Диаграммы - в [Diagrams/](Diagrams/).

## 1. Выбор архитектурного стиля

### Почему не оставить монолит
Система уже работает на пределе (P95 110-120 мс при лимите 100 мс). Рост нагрузки на 20% от нового DSP-партнёра при нелинейном росте задержки (см. AS-IS, «Влияние на время отклика») и штрафные SLA партнёра гарантированно приведут к деградации и штрафам. Монолит нельзя масштабировать по частям, а общая база остаётся потолком всей системы.

### Почему не переписать сразу на микросервисы
Бюджет ограничен, срок промежуточного решения - 3 месяца, в штате нет SRE, архитектура не задокументирована, опыта с брокерами, кешем и контейнерами у команды нет. Одномоментная декомпозиция семи компонентов и разъезд общей базы за 3 месяца - это переписывание системы с высоким риском для непрерывности бизнеса, что прямо запрещено ограничениями.

### Сравнение подходов

| Подход | Суть | Плюсы | Минусы для AdScale |
| ------ | ---- | ----- | ------------------ |
| Модульный монолит | Навести границы между модулями внутри одного деплоя | Дёшево, без сетевых вызовов | Не даёт независимого масштабирования аукциона, общая БД и единый деплой остаются точками отказа |
| Постепенная декомпозиция без фасада | Выделять сервисы по одному, переключая клиентов вручную | Гибкость | Каждое выделение требует менять вызывающие компоненты, нет единой точки переключения и отката |
| **Strangler Fig** | Поставить фасад (API Gateway) перед монолитом и по одному переносить функции в новые сервисы, переключая маршрут | Постепенно, с откатом через маршрутизацию, трафик не прерывается | Период сосуществования монолита и сервисов, нужна синхронизация данных |

**Выбор: Strangler Fig, внутри монолита - модульные границы.** API Gateway становится фасадом, за которым сервисы выделяются по одному в порядке критичности для SLA. Пока компонент не выделен, он живёт модулем монолита с явными границами - это облегчает следующее выделение. Первым выделяется сервис ставок (Auction/Bidding): это единственный компонент, чья задержка напрямую формирует SLA партнёра.

## 2. Промежуточная архитектура (через 3 месяца)

Цель этапа: подключить DSP-партнёра без деградации SLA, держать не менее 18 000 RPS, P95 ≤ 80 мс, разделить критичные и некритичные потоки. Диаграмма: [to-be_three_months.puml](Diagrams/to-be_three_months.puml).

- **API Gateway (Kong)** - фасад Strangler Fig: вход для bid requests DSP-партнёра, аутентификация, rate limiting, мониторинг задержки. Подробно - Task2/api-gateway.md.
- **Bidding Service** выделен из монолита: stateless, контейнер, несколько инстансов за балансировщиком. Ad Server вызывает его по gRPC.
- **Redis** - кеш кампаний, таргетинга, ставок и остатков бюджета перед Ad Server и Bidding Service. Убирает синхронные чтения Postgres из hot path.
- **Kafka (managed)** - события показов и кликов от Delivery Service вместо прямой синхронной записи в Postgres. Statistics пишет в базу пакетами из Kafka. Financial на этом этапе продолжает работать с данными статистики в Postgres, перевод списаний на события из Kafka - на этапе 3.
- **Cache Updater** - заполняет Redis: кабинет публикует изменения кампаний в Kafka, Financial раз в несколько секунд публикует остатки бюджетов активных кампаний. При старте кеш прогревается из read-реплики.
- **Read-реплика Postgres** - для Analytics, тяжёлые запросы больше не конкурируют с аукционом.
- Остальные компоненты (Ad Server, Delivery, Statistics, Financial, Analytics, кабинет) остаются модулями монолита.
- Новые компоненты деплоятся через CI/CD в контейнерах, монолит - по-прежнему, но за Gateway, что позволяет откатывать маршрут.

## 3. Целевая архитектура (через год)

Цель: 50 000 RPS, мультиплатформенная интеграция, микросервисы, событийная обработка, горизонтальное масштабирование, мультирегион, SLA 99,9%. Диаграмма: [to-be_one_year.puml](Diagrams/to-be_one_year.puml).

### Сервисы и обоснование границ

| Сервис | Ответственность | Почему это отдельная граница | Хранилище (владелец данных) |
| ------ | --------------- | ---------------------------- | --------------------------- |
| API Gateway (Kong) | Вход для всего внешнего трафика: DSP/SSP, рекламодатели, события показов/кликов | Единая точка аутентификации, лимитов и мониторинга, фасад Strangler Fig | - (stateless) |
| Ad Server | Приём OpenRTB-запроса, адаптеры партнёров, определение пользователя, подбор кандидатов, оркестрация ответа | Hot path, масштабируется по RPS, изолирует форматы разных партнёров от остальной системы | Redis: сегменты пользователей, индекс таргетинга |
| Bidding Service | Аукцион: взвешивание ставок, бизнес-правила, проверка бюджета, выбор победителя | Самый чувствительный к задержке компонент, свой профиль масштабирования и релизов | Redis: read-модель кампаний и бюджетов (только чтение) |
| Delivery Service | Разметка баннера, приём показов/кликов, публикация событий в Kafka | Трафик конечных пользователей, другой профиль нагрузки, чем у аукциона | Redis: кеш шаблонов креативов |
| Campaign Service | Кампании, креативы, таргетинг, ставки - источник истины | Выделен из бэкенда кабинета: владелец данных, которые читает весь hot path | PostgreSQL |
| Financial Service | Балансы, списания, счета, пополнения через платёжный шлюз | Строгая консистентность и идемпотентность, отдельный контур безопасности | PostgreSQL (журнал проводок) |
| Statistics Service | Приём и агрегация событий показов/кликов | Самая высокая нагрузка на запись, растёт линейно с RPS | ClickHouse |
| Analytics Service | Отчёты и аналитика для рекламодателей | Тяжёлые чтения, не должны влиять на hot path | ClickHouse (свои витрины) |
| Advertiser Dashboard | UI и BFF кабинета | Только UI-логика, данные берёт у сервисов по API | - (данные у сервисов) |

Выбор баз данных по сервисам подробно обоснован в Task3/database-strategy.md.

### Взаимодействие

- **Синхронно, gRPC** - внутри hot path: Ad Server → Bidding Service, Ad Server → Delivery Service. Низкая задержка, строгий контракт (Task2/interaction.md).
- **Синхронно, REST** - кабинет → Campaign, Financial, Analytics. Нагрузка низкая, важна простота.
- **Асинхронно, Kafka** - события показов, кликов, результатов аукциона, изменения кампаний и бюджетов. Потребители: Statistics, Analytics, Financial, обновление кеша (Task3/event-streaming.md).
- **Кеш как read-модель** - hot path не ходит в базы данных. Campaign и Financial публикуют изменения в Kafka, cache updater обновляет Redis (Task3/caching.md).

### Инфраструктура

- Kubernetes: все сервисы в контейнерах, горизонтальное автомасштабирование hot path по RPS и задержке.
- API Gateway (Kong), Kafka с Schema Registry, Redis Cluster, PostgreSQL с Patroni (автоматический failover), ClickHouse с репликацией.
- Наблюдаемость: метрики (Prometheus/Grafana), трассировка по request_id (OpenTelemetry), централизованные логи.
- CI/CD вместо ручного деплоя, canary-релизы для сервисов hot path.

### Мультирегион
Два региона. Hot path (Gateway, Ad Server, Bidding, Delivery, Redis) работает в обоих регионах одновременно (active-active), партнёр направляется в ближайший регион через GeoDNS. Kafka - кластер в каждом регионе, события реплицируются в основной регион через MirrorMaker 2. Campaign и Financial - primary в основном регионе, асинхронная реплика во втором регионе с переключением при аварии региона. Подробно - Task3/failover.md.

### SLA 99,9%
99,9% - это не более ~43 минут простоя в месяц. Достигается за счёт: отсутствия единственной точки отказа на hot path (несколько инстансов, два региона), деградации вместо отказа (ответ «нет ставки» при проблемах зависимостей, Task2/reliability.md), автоматического failover баз, релизов без простоя.

Организационное условие: SLA требует SRE-функции. Найм первого SRE закладывается в бюджет годового плана, не позднее чем за 3 месяца до конца проекта. До этого эксплуатацию упрощают managed-сервисы (Kafka, при возможности Redis и PostgreSQL).

## 4. Дорожная карта

| Этап | Срок | Что делаем | Результат |
| ---- | ---- | ---------- | --------- |
| 1 | 0-3 мес. | Gateway, Bidding Service, Redis, Kafka для событий, read-реплика, CI/CD для новых сервисов | DSP подключён, 18 000 RPS, P95 ≤ 80 мс |
| 2 | 3-6 мес. | Выделение Ad Server и Delivery, Statistics на ClickHouse, Kubernetes для всего hot path | Hot path полностью вне монолита |
| 3 | 6-9 мес. | Выделение Campaign Service и Financial Service с собственными базами, Analytics на ClickHouse | Общая база монолита разделена |
| 4 | 9-12 мес. | Второй регион, отработка failover, кабинет как BFF поверх сервисов, вывод монолита из эксплуатации | 50 000 RPS, мультирегион, SLA 99,9% |

На каждом этапе трафик переключается через Gateway постепенно (сначала малая доля), с возможностью отката маршрута.
