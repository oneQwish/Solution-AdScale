# ADR-001: Эволюция AdScale по паттерну Strangler Fig с первоочередным выделением Bidding Service

**Дата:** 23.09.2026

**Статус:** Принято

## Контекст

Подключение нового DSP-партнёра приведёт к моментальному росту нагрузки на 20% и вдвое через год. Требования партнёра: стабильный ответ не более 80 мс, штрафы за деградацию и downtime.

Система в текущем виде не может обеспечить соблюдение SLA: P95 на отметке 110-120 мс при текущем лимите 100 мс (см. AS-IS.md). Срок приведения системы в готовность к подключению - 3 месяца. Финальная цель через год - микросервисы, событийная обработка, 50 000 RPS, мультирегион, SLA 99,9%.

Бюджет ограничен, полная переработка сервиса невозможна: требует дополнительных материальных и трудовых затрат (текущий штат 35 человек) с обязательным обеспечением непрерывности бизнеса. В штате нет SRE, нет опыта эксплуатации кеша, очередей, контейнеризации.

Модульный монолит оценён как самостоятельный стиль без выделения сервисов: границы модулей не дают независимого масштабирования аукциона, общая БД и единый деплой остаются точками отказа, поэтому по SLA, надёжности и масштабируемости он близок к монолиту.

## Рассмотренные альтернативы

### Альтернатива 1: Оставить монолит
Отклонено. Система уже нарушает свой текущий лимит, рост нагрузки только усугубит деградацию.

### Альтернатива 2: Модульный монолит
Отклонено как целевой стиль. Наводит порядок в коде, но не решает главную проблему: аукцион нельзя масштабировать отдельно от остальных модулей, общая база остаётся узким местом и точкой отказа. Используется как промежуточное состояние компонентов, которые ещё не выделены.

### Альтернатива 3: SOA
Отклонено. Крупные сервисы с общей шиной требуют сопоставимых с микросервисами усилий на выделение, но не дают мелкой гранулярности масштабирования, нужной hot path. Финальные требования (микросервисы, горизонтальное масштабирование) SOA закрывает хуже.

### Альтернатива 4: Полный переход на микросервисы сразу
Отклонено. Бюджет, срок 3 месяца и отсутствие SRE делают безопасную декомпозицию и обкатку всей системы за это время нереалистичной - подтверждается матрицей (78, несмотря на лучший результат по SLA и масштабируемости).

### Альтернатива 5: Strangler Fig
Выбрано. Перед монолитом ставится фасад (API Gateway), новые сервисы выделяются по одному, трафик переключается маршрутом с возможностью отката. Сохраняет почти все плюсы микросервисов по SLA и масштабируемости, при этом не требует одномоментного переписывания и не угрожает непрерывности бизнеса.

## Решение

1. API Gateway (Kong) ставится перед монолитом как фасад Strangler Fig.
2. Первым выделяется Auction/Bidding Service: stateless, контейнеры, несколько инстансов за балансировщиком. Это единственный компонент, чья задержка напрямую формирует SLA партнёра - фактор с весом 5.
3. На первом этапе данные остаются в общей Postgres, разъезд не одномоментный. Redis - read-only кеш кампаний, ставок и бюджетов перед hot path. Kafka разгружает запись кликов/показов (ADR-003). Read-реплика добавляется для Analytics.
4. Невыделенные компоненты остаются модулями монолита с явными границами и API.
5. Порядок выделения: hot path (Ad Server, Delivery) → Statistics → Campaign и Financial с собственными базами → Analytics. Через год монолит выводится из эксплуатации (дорожная карта - TO-BE.md).

## Последствия

### Положительные
Независимое масштабирование самого критичного по SLA компонента уже через 3 месяца. Снижение blast radius - падение Bidding Service не тянет за собой остальной монолит, а падение модулей монолита не останавливает аукцион. Read-only кеш и Kafka снимают конкуренцию за БД без немедленного разъезда данных. Каждый шаг миграции откатывается переключением маршрута на Gateway.

### Отрицательные
Сетевой вызов вместо internal call между Ad Server и Bidding Service - риск для latency, если не продумать протокол (решается gRPC и бюджетом задержки, см. Task2). Read-only кеш требует стратегии инвалидации (см. Task3/caching.md) - иначе устаревшие бюджеты/ставки. Stats/Analytics делят БД с частью монолита до разъезда данных. Период сосуществования монолита и сервисов требует синхронизации данных через события.

Формальный SLA 99,9% и мультирегион не гарантированы без SRE-функции. Найм SRE (не позднее чем за 3 месяца до конца годового горизонта) закладывается в бюджет. До этого эксплуатацию упрощают managed-сервисы.

Задачи SRE после найма: мониторинг/алертинг по latency и SLO, health-check и автофейловер для hot path, эксплуатация Kafka и Redis, пороги Circuit Breaker/Retry, безопасный CI/CD вместо ручного деплоя в prod, on-call и runbook'и, capacity planning под дальнейший рост.

## Критерий успеха
Через 3 месяца: DSP-партнёр подключён, 18 000 RPS при P95 ≤ 80 мс. Через год: монолит выведен из эксплуатации, 50 000 RPS, работа в двух регионах.
