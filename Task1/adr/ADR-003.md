# ADR-003: Kafka выбрана для потоковой обработки событий

**Дата:** 2026-09-13

**Статус:** Принято

## Контекст

Клики и показы сейчас пишутся напрямую в общую PostgreSQL - это одна из причин, почему компоненты конкурируют за ресурсы базы и есть риск потерять данные на пиках.

Нужно убрать эту запись с горячего пути аукциона и перенести в отдельный канал, который читают минимум три потребителя независимо друг от друга: Statistics Service (пишет в Postgres), Analytics Service (строит отчёты) и, через год, Financial Service (сводит балансы по расходам на рекламу).

Событий будет расти вместе с общей нагрузкой: 18 000 RPS через 3 месяца, 50 000+ RPS через год, плюс событие результата каждого аукциона, то есть поток событий сопоставим с RPS самого аукциона.

У команды нет опыта с очередями и брокерами сообщений, контейнеров тоже никогда не было. SRE появится не раньше чем за 3 месяца до конца года. Бюджет ограничен. Стек смешанный - C++, Go, Python, Node.js - нужна развитая поддержка библиотек под все четыре языка.

Рассматривал три варианта:

### Вариант 1: Kafka
Выбрано. Умеет держать несколько независимых читателей на одном потоке без потери данных - именно то, что нужно для Stats, Analytics и Financial одновременно. Под наш стек есть зрелые клиентские библиотеки (librdkafka для C++, клиенты для Go, Python и Node.js). Tradeoff - простота обслуживания. Нужно готовить команду к поддержке решения.

### Вариант 2: RabbitMQ
Не подходит. Проще в обслуживании, чем Kafka. Классические очереди RabbitMQ удаляют сообщение после подтверждения: чтобы три читателя получали один поток независимо, нужна отдельная очередь под каждого, повтора событий нет. С версии 3.9 в RabbitMQ есть Streams - журнал с повтором и независимыми читателями, но это более молодая часть продукта с меньшей экосистемой (коннекторы, Schema Registry, интеграция с ClickHouse) и меньшим опытом эксплуатации на потоках 50 000+ событий в секунду.

### Вариант 3: Redis Streams
Не подходит. Умеет держать несколько независимых читателей (consumer groups) технически так же, как Kafka. Но Redis Streams хранит историю в оперативной памяти - чтобы Financial Service мог наверстать пропущенное без потери данных, историю нужно копить надолго, а держать большой объём в RAM дорого при быстром росте бизнеса.

## Решение

Kafka становится единой шиной для кликов, показов и обновлений кампаний. У неё независимые потребители: Statistics, Analytics, Financial и Cache Updater (обновление кеша для hot path). Первые 3 месяца разворачиваем её как облачный managed-сервис, не сами - так снимаем единственный минус Kafka (сложность обслуживания), не меняя саму технологию. Переходить на самостоятельное обслуживание (если вообще понадобится) будем позже, отдельным решением, когда команда наберётся опыта.

## Последствия

### Плюсы
Три потребителя читают один и тот же поток, не мешая друг другу и не теряя данные, даже если один из них упадёт - это особенно важно для Financial Service, там потеря события прямо ведет к потере денег. Пропускной способности хватит с запасом на рост после 50 000 RPS. Можно переиграть события заново, если в коде потребителя был баг. Managed-режим снимает с команды нагрузку, которую она бы не потянула сама за 3 месяца без опыта.

### Минусы и риски
Сама модель Kafka всё равно не простая - партиционирование, отставание потребителей, перебалансировка - команде придётся освоить это в любом случае, managed-режим снимает только инфраструктуру, а не саму логику работы с ней в коде. За managed-сервис надо платить, и бюджет ограничен - если недооценить объём трафика в начале, можно либо переплатить, либо взять кластер меньше, чем нужно. Managed-сервис конкретного облака - это дополнительная привязка к поставщику, переход на другого потом потребует работы. Команде нужно время, чтобы разобраться с моделью offset'ов и consumer group - это нужно заложить в план на 3 месяца, а не считать as-is.

## Критерий успеха
Через 3 месяца: отставание потребителей остаётся низким при 18 000 RPS, ни одно событие не теряется при рестарте любого из трёх потребителей. Через год: поток держит 50 000+ RPS без деградации, Financial Service сводит балансы без ручного вмешательства.
