# AS-IS: диагностика текущей архитектуры

AdScale это SaaS-платформа, работающая с рекламодателями, функционал: работа с рекламными кампаниями, управление бюджетами и ставками, участие в RTB аукционах, показ рекламы пользователям сайтов и приложений, сбор аналитики и формирование отчетности для клиентов.  

## Обзор системы
Гибридный монолит на C++ / Go / Python / Node, PostgreSQL, деплой производится вручную сразу в production. Компоненты приложения:
1. Рекламный сервер (C++, Go)
2. Сервер аукциона (C++)
3. Сервис выдачи (Node.js)
4. Сервис статистики (Python)
5. Финансовый сервис (Go)
6. Сервис аналитики (Python)
7. Рекламный кабинет (Node.js, JavaScript)

**Общая база данных PostgreSQL**.
**Кеша, очередей и контейнеризации нет.**

### Внешние связи
1. DSP-партнер (OpenRTB)
2. Платежный шлюз
3. Пользователи сайта/приложения

Система поддерживается командой из 35 человек, backend-, frontend- и DevOps-разработчики, тестировщики, дизайнеры, сотрудники службы поддержки, менеджмент.
**Нет выделенного SRE, техписателя, бизнес-аналитика.**

Текущее решение позволяет поддерживать штатную работу сервисов, но пиковые нагрузки приводят к деградации времени отклика (15 000 RPS в пике, P95 110–120 мс при требовании ≤100 мс, запаса по производительности нет).

## Путь запроса (hot path)
DSP-партнёр отправляет bid request в Ad Server. Ad Server синхронно читает из Postgres данные для таргетинга и передаёт кандидатов в Auction Engine. Auction Engine так же синхронно читает из Postgres ставки и кампании, определяет победителя и передаёт его в Delivery Service. Delivery Service внутренним вызовом регистрирует показ в Statistics Service, который пишет событие напрямую в Postgres.

Итого на пути ответа DSP-партнёру стоят два последовательных синхронных чтения из одной базы - их время складывается. Третье обращение (запись события через Statistics Service) нагружает ту же базу и конкурирует с этими чтениями.

## Масштабирование

Горизонтальное масштабирование монолита в текущем виде проблему не решает:

1. Компоненты нельзя масштабировать по отдельности. Чтобы добавить мощности Ad Server и Auction Engine, придётся копировать весь монолит вместе с аналитикой и кабинетом.
2. Каждая новая копия открывает свои соединения к Postgres. В Postgres одно соединение - отдельный процесс, число соединений ограничено, поэтому новые инстансы усиливают конкуренцию за ту же базу.
3. Сама база масштабируется только вертикально - это потолок всей системы.
4. Контейнеризации нет, деплой ручной - быстро добавить инстансы под пиковую нагрузку нельзя.

Дополнительные инстансы снизят риск остановки из-за падения одного экземпляра приложения, но риск отказа БД останется, а нагрузка на неё вырастет.

## Влияние на время отклика

В теории очередей время ожидания в очереди к ресурсу растёт примерно как **1 / (1 - ρ)**, где ρ - загрузка ресурса. Это упрощённая модель, она даёт оценку порядка величины: при загрузке 50% ожидание условно x2, при 90% - x10.

У AdScale предельно загружены пул соединений и I/O базы. На пути ответа DSP-партнёру стоят два последовательных синхронных обращения к ней, и каждое добавляет своё ожидание в очереди. Поэтому уже при 15 000 RPS P95 составляет 110-120 мс, а в часы пик возникают периодические деградации.

При 18 000 RPS (+20%) задержка вырастет нелинейно: превышение лимита 100 мс гарантировано, требование партнёра в 80 мс без изменения архитектуры недостижимо.

## Организационные риски

1. Нет SRE: нет ответственного за SLA и дежурства.
2. Архитектура не задокументирована: затруднено эволюционное развитие сервиса, знания о системе держатся на отдельных людях.
3. Деплой производится вручную: каждый релиз увеличивает риск простоя и штрафов.
4. Нет BA: требования DSP-партнёра ложатся напрямую на разработчиков.

## Выводы

1. Главная причина превышения задержки - синхронные обращения к общей БД на пути ответа DSP-партнёру. Их нужно убрать из hot path (кеш данных кампаний, ставок и таргетинга).
2. Запись событий и аналитика конкурируют с аукционом за одну базу. Критичные и некритичные потоки нужно разделить: события через очередь, аналитика на отдельной реплике.
3. PostgreSQL - одновременно главное узкое место и главная точка отказа. Нужны репликация и отказоустойчивость базы.
4. Монолит не позволяет масштабировать только критичные компоненты. Аукцион и ставки нужно выделить в отдельно масштабируемый сервис.
5. Ручной деплой и отсутствие SRE делают любое изменение рискованным. Контейнеризация, CI/CD и мониторинг задержки входят в план с первого этапа.
